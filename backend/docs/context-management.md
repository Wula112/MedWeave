# Agent 上下文压缩

各专科的 `create_agent` 使用 LangChain `SummarizationMiddleware`，在模型调用前检查消息历史。达到预算时，较早消息会被摘要替换，近期消息继续保留；压缩后的历史会回写主图，供后续轮次和专家转接使用。工具调用与结果的边界由 LangChain 处理。问诊的结构化事实仍由问诊子图单独维护。

## 配置模型容量

1. 若配置了 `LLM_CONTEXT_WINDOW`，将其作为当前聊天模型的最大输入 Token 容量；它必须是不小于 1024 的整数。
2. 否则读取当前 LangChain 模型 profile 的 `max_input_tokens`。
3. 如果 profile 不提供容量，记录警告并保守回退至 8192 Token。

自定义 OpenAI 兼容模型和火山方舟推理接入点常使用无法识别的模型名或 endpoint ID，应按照实际部署的模型容量设置环境变量。切换模型时记得同步更新。例如：

```dotenv
LLM_CONTEXT_WINDOW=32768
```

## 预算计算

设模型容量为 `W`。系统提示词（包括注入的 RAG 内容）与工具 Schema 按实际文本估算，固定开销至少预留 `W` 的 9%；此外分别预留 15% 用于工具结果增长、9% 用于估算误差、5% 用于模型输出或共享窗口的余量。剩余部分为历史预算。`trigger` 取历史预算的 67%，最多 32000；`keep` 取 trigger 的 29%，最多 8000。

以 32768 Token、固定开销未超过最低预留为例，trigger 约为 13600，keep 约为 3900。系统提示词或工具 Schema 更大时，历史预算会相应减少。计算出的窗口、固定开销、trigger 和 keep 会以数值写入应用日志，不记录消息内容。

Token 计数使用 LangChain 的近似计数器，初始设置为每 Token 约 2 个字符，并对完整历史和部分消息采用相同口径。该值并不等同于任何供应商的精确 tokenizer；应结合模型真实用量和中文、工具结果的分布校准。摘要输入不使用默认的 4000 Token 裁剪上限，摘要提示要求保留病史、过敏、用药、数值、否定信息和不确定性。摘要调用遵循现有模型超时与重试策略；失败或返回空内容时会中止本次调用，避免以错误文本覆盖历史；内部摘要不会作为普通回复流向客户端。

压缩不是严格的上下文溢出防护：单条超长消息、过大的工具结果、动态 RAG 提示或多模态内容仍可能超过模型容量。工具输出和检索内容仍需合理控制；容量配置、摘要频率、真实输入峰值及关键信息保留率应在实际流量中验证。历史在当前状态中被替换，已有检查点和客户端聊天记录不会因此自动删除。
